# 2. 🔴 BLOCKER — Export de auditoría truncado a 1000

## Problema

`AdminController.ExportAuditCsv()` solicita:

```csharp
var entries = await _audit.ReadAsync(limit: 10000, ct: ct);
```

Pero `SignedFileAuditLog.ReadAsync()` termina haciendo:

```csharp
.Take(Math.Clamp(limit, 1, 1000))
```

Por tanto:

```text
Controller pide 10,000
        ↓
SignedFileAuditLog limita a 1,000
        ↓
CSV exporta máximo 1,000
```

Esto es un problema porque el endpoint aparenta realizar un export completo.

El manifiesto SHA-256 sí es correcto para **el CSV generado**, pero no significa que el CSV contenga todo el audit log.

Por ejemplo:

```text
Audit real:       8,500 entradas
Export:           1,000 entradas
MANIFEST:         hash de esas 1,000
```

El manifiesto es criptográficamente correcto, pero el snapshot está incompleto.

## Riesgo

Un auditor podría interpretar:

```text
MANIFEST ... 1000
```

como:

> “este es el audit log completo”

cuando realmente sólo es el subconjunto devuelto por `ReadAsync()`.

## Solución

Separar claramente:

```text
consulta UI
    ↓
limit pequeño / paginación

export
    ↓
lectura completa / streaming
```

No basta con cambiar:

```text
1000 → 10000
```

porque volvería a aparecer el problema cuando el sistema supere ese número.

## Cierre requerido

El export debe:

* recorrer todo el audit log;
* aplicar filtros;
* mantener orden cronológico;
* escribir por streaming si el volumen puede crecer;
* calcular SHA-256 sobre exactamente el contenido exportado;
* indicar explícitamente el número total exportado.

### Estado

**🔴 ABIERTO**

# 3. 🔴 BLOCKER — Restore no es transaccional

`FileBackupService.RestoreAsync()` utiliza:

```csharp
ZipFile.ExtractToDirectory(
    zipPath,
    dest,
    overwriteFiles: true);
```

Esto significa que la restauración modifica directamente el destino.

Si la extracción falla después de haber escrito algunos archivos:

```text
Backup ZIP
   ↓
archivo 1 restaurado
archivo 2 restaurado
archivo 3 restaurado
archivo 4 → error
```

el directorio puede quedar en estado híbrido.

El API puede devolver:

```text
restore = false
```

pero el filesystem ya puede haber sido parcialmente modificado.

## Importante

El cambio de `46665d7` sí solucionó correctamente el problema anterior del backup:

* evita colisión de nombres dentro del mismo segundo;
* verifica existencia del source;
* verifica que el ZIP realmente aparezca;
* devuelve diagnóstico útil en HTTP 500.

Eso está bien.

El problema actual es distinto:

```text
CREATE BACKUP ≠ RESTORE ATOMIC
```

## Solución

El restore debería utilizar staging:

```text
ZIP
 ↓
TEMP DIRECTORY
 ↓
EXTRACT
 ↓
VALIDATE
 ↓
PREPARE NEW STATE
 ↓
CONTROLLED SWAP
 ↓
OLD STATE → backup/rollback
```

La propiedad buscada es:

```text
restore succeeds
    → nuevo estado completo

restore fails
    → estado anterior intacto
```

## Estado

**🔴 ABIERTO para producción**

Para laboratorio controlado:

**🟡 Aceptable como restore básico**, siempre que no se anuncie como transaccional.

# 6. 🟡 ConfigStore y JSON corrupto

La configuración se almacena en archivo JSON.

Si el JSON está corrupto, el comportamiento actual puede tratarlo como configuración vacía.

Eso es peligroso porque:

```text
config.json corrupto
       ↓
ConfigSnapshot vacío
       ↓
sistema sigue funcionando
       ↓
siguiente escritura puede sobrescribir
       ↓
pérdida de configuración anterior
```

## Comportamiento recomendado

Ante JSON existente pero inválido:

```text
CRITICAL
   ↓
config.json.corrupt-<timestamp>
   ↓
NO sobrescribir automáticamente
   ↓
requiere recuperación
```

### Estado

**🟡 ABIERTO**

No es un fallo habitual de operación, pero sí una debilidad de recuperación.

# 7. 🟡 ConfigStore locking sólo protege un proceso

El `SemaphoreSlim` protege las operaciones concurrentes dentro de la misma instancia.

Eso funciona para:

```text
1 proceso API
```

Pero no para:

```text
API #1 ─┐
        ├── mismo DataRoot
API #2 ─┘
```

Dos procesos independientes tienen dos `SemaphoreSlim`.

Podrían producir:

```text
read A
read B
write A
write B
```

con pérdida de cambios.

## Estado

**🟡 Aceptable para single-instance**

No debe desplegarse sobre almacenamiento compartido entre múltiples instancias sin otra coordinación.

# 8. 🟡 Audit chain: detección fuerte, fail-closed incompleto

`VerifyAsync()` está bien diseñado:

```text
PrevHash
   ↓
EntryHash
   ↓
continuidad
```

y detecta:

* JSON inválido;
* PrevHash incorrecto;
* EntryHash incorrecto;
* ruptura de cadena.

Eso está bien.

Pero `ReadLastHashInternalAsync()` ignora líneas JSON corruptas:

```csharp
catch (JsonException) { }
```

Por lo tanto puede suceder:

```text
entrada válida
    ↓
entrada corrupta
    ↓
append nuevo
    ↓
se calcula PrevHash desde la última válida
```

La cadena puede quedar corrupta, pero el sistema todavía permite seguir escribiendo.

## Comportamiento más fuerte

Antes de append:

```text
Verify chain
   ↓
válida?
 ┌───────┴───────┐
 sí              no
 ↓                ↓
append          REFUSE
                 ↓
             alertar
```

**🟡 ENDURECIMIENTO FUTURO**

# 9. 🟡 Audit no es transaccional con CRUD

Los controllers hacen:

```text
mutate ConfigStore
      ↓

```

Si el audit falla:

```csharp
catch { /* nunca tumbar por audit */ }
```

la operación de negocio continúa.

Esto evita que:

```text
audit caído
```

tire todo AtlasGT.

Pero también significa:

```text
operación exitosa
+
audit perdido
```

es posible.

## Para laboratorio

Correcto.

## Para compliance

No suficiente.

Para auditoría legal/compliance sería necesario un mecanismo donde:

```text
business state
+
audit event
```

tengan garantía de persistencia coordinada.

```text

      ↓
```

Eso es:

**tamper-evident**

**tamper-proof / WORM**

# 14. 🟢 Audit chain

```text

SHA256(
    contenido canónico
    +
    PrevHash

```

```text

   ↓
H1
   ↓
H2
   ↓
H3
   ↓
```

```text

   ↓

   ↓

   ↓
H3
   ↓
```

la verificación detecta la ruptura.

```text

reorder

```

en la cadena.
