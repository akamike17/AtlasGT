# 1. Diagnóstico forense previo — NO ignorar

La revisión del commit `aac25d3` encontró que el concepto es válido, pero la implementación actual **no debe considerarse todavía un conector industrial universal ni producción-ready**.

Hallazgos confirmados directamente en el commit:

### CRÍTICO — Conectividad simulada
`GenericProtocolConnector.ConnectAsync()` no abre un socket ni un puerto serial. Cambia el estado después de un `Task.Delay(100)` y devuelve `true`.

`ReadAllAsync()` tampoco recibe datos de un dispositivo: llama a `SimulateIncomingData()`, genera bytes aleatorios con `Random().NextBytes(...)` y los entrega como `RawSample`.

Por lo tanto:

```text
aac25d3:
ConnectAsync → SIMULACIÓN
ReadAllAsync → BYTES ALEATORIOS
```

Esto debe desaparecer del runtime de producción y quedar únicamente detrás de un transporte de prueba/simulador explícito.

### CRÍTICO — Checksum/CRC no implementado
`ValidateFrame()` detecta `EnableChecksum`, escribe un log y posteriormente devuelve `true`.

No existe cálculo ni comparación real de CRC/checksum.

No se puede afirmar soporte de CRC mientras esto siga así.

### CRÍTICO — Little Endian no implementado
`ProtocolDecoder` contiene la rama para `Endianness.Little`, pero no modifica el slice. Después utiliza siempre las variantes `BigEndian` de `BinaryPrimitives` para `Int32`, `UInt32`, `Float32` y `Float64`.

Esto significa que el schema puede declarar Little Endian pero el decoder actualmente interpreta Big Endian.

### ALTO — Framing incompleto
El enum declara:

- `FixedLength`
- `Delimiter`
- `LengthPrefix`

pero el runtime únicamente valida `FixedLength`. Delimiter y LengthPrefix no tienen una implementación completa demostrada.

### ALTO — BitField declarado pero no soportado
`EncodingType.BitField` existe en el schema, pero `ProtocolDecoder` termina en `NotSupportedException` para ese caso.

No debe aparecer como capacidad soportada hasta implementarlo y probarlo.

### ALTO — Decoder separado del pipeline
Existe `ProtocolDecoder`, pero el `GenericProtocolConnector` actual entrega el `RawSample` sin demostrar el flujo:

```text
transport → frame → validation → decoder → fields → normalization
```

Hay que integrar y probar ese pipeline.

### ALTO — Request/Response insuficiente
El schema actual describe transporte/framing/fields, pero no modela de forma suficiente una operación del tipo:

```text
REQUEST → WAIT → MATCH RESPONSE → DECODE
```

Para que el sistema sea realmente útil para protocolos desconocidos, se necesita una capa declarativa de operaciones.

### ALTO — Safety de escritura insuficiente
`CommandSafetyService` mantiene un `HashSet<string>` de endpoints habilitados y valida principalmente la longitud en FixedLength. El comentario menciona patrones prohibidos, pero no existe una política industrial real de allowlist/comando/auditoría/autorización.

No debe venderse como seguridad industrial certificada.

### MEDIO — `ConnectionString` como string genérico
`DeviceConfig.ConnectionString` permite almacenar información sensible como texto plano. Debe revisarse la separación entre endpoint/configuración y secretos.

### MEDIO — Alcance del commit mezclado
El commit incorpora Generic Protocol pero también agrega/ajusta piezas de alertas, device configuration, Swagger, OpenTelemetry, Docker y documentación. Antes de cerrar H1 debe comprobarse que no se generó deuda lateral ni funcionalidad falsa.

# 37. Principio rector

> **AtlasGT no necesita conocer todos los protocolos del mundo. Necesita poder describir, ejecutar, validar y decodificar protocolos nuevos de forma determinista sin recompilar el producto por cada protocolo.**

Pero la afirmación solo vale cuando el repositorio la demuestra.

**Trabaja duro. No maquilles. No simules PASS. No cierres por compilación.**

El objetivo no es que el Generic Protocol Connector parezca universal.

El objetivo es que, después de H1, podamos tomar un protocolo documentado, escribir su schema, ejecutar el runtime y demostrar con bytes, pruebas y logs exactamente qué ocurrió.
